# SOIT Community Release Process

SOIT Community releases are created only from a clean, reviewed tag matching
`vMAJOR.MINOR.PATCH`. The tag version must match `server/pyproject.toml`,
`web/package.json`, `cli/pyproject.toml` together with `__version__` in
`cli/soit_cli/__init__.py`, runtime manifests, and release notes under
`docs/releases/`.

The tag-triggered `.github/workflows/release.yml` reruns release checks and builds
three images used by the default topology: `server`, `knowledge-worker`, and
`web`. It publishes digest-addressable images, SPDX JSON SBOMs, GitHub/Sigstore
build provenance and SBOM attestations, a deterministic `git archive`, and
`SHA256SUMS`. The workflow creates the GitHub Release only after these steps pass.
The same tag publishes the `soit` command line to PyPI as
[`soit-ai-cli`](https://pypi.org/project/soit-ai-cli/): the `publish-cli` job
builds the wheel and sdist from `cli/` with `uv build`, checks that their file
names carry the tag version, and uploads them through PyPI trusted publishing
(see below), with PEP 740 attestations generated by the publish action. The
job runs next to the image builds and does not gate the GitHub Release, so a
failed upload is retried by rerunning the job, not by cutting a new tag; a
version that PyPI already holds cannot be uploaded again.

Before pushing a tag:

1. Confirm the worktree and index are clean and the candidate commit is reviewed.
2. Confirm `quality.yml` and `security.yml` pass on that exact commit.
3. Complete fresh-install, N-1 migration, backup/restore, and independent product
   acceptance evidence outside the public repository.
4. Review release notes and known limitations. Do not label planned or locally
   simulated capabilities as available.
5. Create an annotated tag on the approved commit and push the tag only after
   release approval.

After publication, copy the real tag, commit, image digests, SBOM checksums, and
attestation URLs into an evidence document based on
`docs/deployment/release-artifacts.example.json`, then run:

```powershell
cd server
uv run python scripts/verify_release_artifacts.py `
  ../artifacts/release/release-artifacts.json
```

## PyPI trusted publisher (one-time setup)

`publish-cli` carries no PyPI token. PyPI accepts the GitHub Actions OIDC
token of the job instead, once a trusted publisher is registered on the
project. This is done once by a PyPI account that will own the project:

1. Sign in to PyPI and open **Your projects › Publishing** (or, once the
   project exists, its **Manage › Publishing** page).
2. Add a GitHub publisher with exactly these values:
   - PyPI project name: `soit-ai-cli`
   - Owner: `soit-ai`
   - Repository name: `soit`
   - Workflow name: `release.yml`
   - Environment name: `pypi`
3. In the GitHub repository, create the `pypi` environment under
   **Settings › Environments**. Restricting it to tags matching `v*` and adding
   a required reviewer are optional; the workflow already only runs on tags.

Before the first upload the entry is a *pending* publisher; PyPI creates the
project and turns it into a normal publisher when the first release arrives.
The first upload happens on the next `v*.*.*` tag; nothing is published from
branches or pull requests. The distribution name is `soit-ai-cli` because
`soit` and `soit-cli` belong to unrelated projects on PyPI; the installed
command is still `soit`.

Consumers should verify downloaded files with `sha256sum -c SHA256SUMS` and verify
GitHub artifact attestations with `gh attestation verify`. The release is not
complete while any tag, commit, digest, checksum, SBOM, provenance record, or
release note points to a different build.
