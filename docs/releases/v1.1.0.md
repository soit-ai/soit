# SOIT v1.1.0 Governance Release Notes

Status: release evidence template. Publish only after the release commit is tagged as `v1.1.0` and the governance release evidence verifier passes against real command output.

## Highlights

- Plugin-first governance: MCP server and Skill artifacts are installed and governed through the Plugin module.
- Governed runtime calls: plugin-owned tools use policy gateways for workspace access, egress checks, controlled secret injection, audit evidence, and cost attribution.
- Observe governance surfaces: run replay, Audit Explorer, cost attribution, tool call evidence, citations, child runs, and response events are available from Observe.
- Regression as release gate: historical runs can become regression cases, and Agent publish can replay active cases before writing a release.
- Governance demo: the 20-minute demo covers permissions, secrets, call audit, cost attribution, replay, and regression evidence.
- Versioned policy: every save of a workspace's egress rules and usage limits appends a revision that can be read, compared and restored, and the policy in force carries a content-derived identifier that refused requests are recorded against.
- Approvals as records: a run that stops for a decision writes the request to the governance ledger, so the task can be opened and answered by someone who was not watching the stream, and the decision is recorded against the tool call that raised it.
- Content safety in the box: a deterministic in-process provider inspects content entering and leaving the runtime for credentials and personal identifiers, redacting the former and recording the latter, with findings in run evidence and never the matched text.
- Accounts and sessions: sessions can be listed and ended, TOTP second factors enrolled and required per workspace, and an account closed on request with a withdrawal period.
- Schedules: cron-driven executions hand work to the same durable path the API uses, so a scheduled run is an ordinary run.
- Counted listings: runs, run steps, audits and tasks report how many rows match the filters, and the audit ledger can be narrowed by actor, object, outcome and time window.
- Five-container lite profile: `docker compose -f docker/docker-compose.lite.yml up -d` runs every feature on PostgreSQL with pgvector, Redis, the API, the web UI and one worker, with secret values sealed in the database so they survive restarts.
- Declared means enforced: private knowledge bases stay with their creator, owners, admins and grantees; a workflow's `spec.limits` stop the run; an agent run whose approvals are decided on the approvals page finishes by itself; and concurrent credit deductions book serially with one alert per threshold crossing.

## Database Compatibility

- Fresh installations migrate from `base` to `20260926110000`.
- The supported N-1 upgrade range is `20260803090000..20260926110000`.
- Older or unknown development snapshots require a new database or an
  operator-managed export/import path.

This release adds tables for user sessions, saved views and pins, second
factors, account deletion requests, identity tokens and workspace invitations,
schedules, and policy revisions, and adds review-state columns to agent
versions. Every one is additive; no existing column changes meaning. The last
two revisions (`20260917100000`, `20260917120000`) only drop indexes that a
composite index already covers and add one partial index on the outbox; they
change no data, and both downgrade cleanly.

`20260926100000` is the one data migration: knowledge visibility is now
enforced, so every existing `private` knowledge base is set to `workspace`,
which keeps the access members had before the upgrade. Mark a knowledge base
`private` again to limit it to its creator, workspace owners and admins, and
members holding a resource grant on it. The downgrade leaves the rows as they
are.

## Upgrading a Production Deployment

1. Run `alembic upgrade head` (the `migrate` service does this before the API
   starts).
2. Deploy the new `response-worker` service from
   `docker/docker-compose.production.yml`. The API no longer executes chats:
   it sets `RESPONSE_INTERACTION_WORKER_IN_API=false`, so without a running
   `response-worker` accepted chats wait in the queue.
3. Keep the worker's `stop_grace_period` longer than
   `RESPONSE_INTERACTION_WORKER_DRAIN_SECONDS` so a rolling restart releases
   in-flight chats to another replica instead of leaving them to expire.
4. Size PostgreSQL `max_connections` for one more process
   (docs/operations/database-connections.md), and add response-worker
   replicas, not per-process concurrency, for more chat capacity.
5. Agent response verification is now opt-in (`policies.verify: true`);
   versions that relied on the default will answer with one model call.
6. Knowledge bases that should stay with their creator must be marked
   `private` after the upgrade: the migration opens every existing one to its
   workspace, and new knowledge bases default to `workspace`.

`docker/.env.production.example` lists every value the production compose file
reads.

## Known Limitations

- Content safety is pattern matching, not classification. The built-in provider
  finds credentials and the identifiers that are personal data everywhere; it
  cannot judge tone, intent, jailbreaks or confidentiality. A deployment that
  needs those points `CONTENT_SAFETY_PROVIDER=http` at a classifier it operates.
- Draft review is a state on the version, not a review object. There is no
  review thread, assignee or ticket.
- An agent run resumes by itself once its approvals are decided anywhere. A
  workflow run waiting for approval does not: after deciding, resume it with
  the run's Resume action (`POST /api/v1/workflows/{id}/runs/{run_id}/resume`),
  because workflows execute in the process that starts them and have no
  queued worker to hand the resume to yet.
- The console reports no marketplace, seat licensing or SSO configuration:
  those belong to SOIT Enterprise and SOIT Cloud.
- The MCP adapter targets the MCP SDK v1 line over streamable HTTP with the
  `client_credentials` grant; the browser-based authorization-code flow and
  the stateless 2026-07-28 protocol revision are not supported.
- The workflow builder ships 8 core node types plus plugin-exported node
  types; loop, code-execution, and parameter-extraction nodes are not
  included.
