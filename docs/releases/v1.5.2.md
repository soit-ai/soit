# SOIT v1.5.2 Security Release Notes

Status: prepared on 2026-10-02; not yet tagged.

A security patch on v1.5.1. Upgrade every v1.5.x installation; earlier
versions carry the same two flaws.

## Security

- **Resource grants took only write permission.** `POST` and `DELETE
  /api/v1/resource-grants` checked that the caller could write to the
  workspace, not that they could govern it, so any member with the
  Developer role could grant themselves every action on any resource,
  including a private knowledge base, agent or workflow, and so read or
  change it. Granting and revoking now take a workspace Owner or Admin.
- **A document's `file_id` was taken as given.** Uploading a document with
  a `file_id` stored that key as the document's file, and downloading the
  document read it. A member who could update one knowledge base could name
  another base's file, a private one included, and download it. `file_id`
  must now name a file under the same knowledge base's storage prefix; any
  other is refused with `400`.

Both are covered by tests that fail on v1.5.1.

## Database Compatibility

- Fresh installations migrate from `base` to `20261001110000`.
- This release adds no migrations: a v1.5.1 database needs none.
- The supported N-1 upgrade range stays `20260927160000..20261001110000`.

## Upgrading

1. Nothing to migrate. Restart the API and workers on the new images.
2. Behaviour changes to review:
   - A member with the Developer role who managed grants under
     **Govern › Access** now gets `403`; ask a workspace Owner or Admin.
   - A client that uploaded documents with a `file_id` of its own must
     upload the file instead, or name a file already stored for the same
     knowledge base.
3. Review the audit ledger for grants made by members who were not Owners or
   Admins (`identity.resource_grant.changed`, its actor), and revoke any that
   should not exist.

## Known Limitations

- The known limitations of v1.5.0 still apply.
