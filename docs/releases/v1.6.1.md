# SOIT v1.6.1 Approval Fixes Release Notes

Status: prepared on 2026-10-03; not yet tagged.

A patch on v1.6.0 for three approval defects. Upgrade every installation
that gates tool calls on approval; earlier versions carry the same defects.

## Fixed

- **A workflow resume ignored the approval decision.** Resuming a workflow
  run that stopped for approval (`POST
  /api/v1/workflows/{id}/runs/{run_id}/resume`) skipped the tool node's
  approval gate without reading the request, so a call a reviewer rejected,
  or nobody had decided yet, ran once anyone allowed to run the workflow
  resumed it. Resuming now reads the request the run waits on:
  - pending or missing: `409`, and the run keeps waiting;
  - rejected, canceled or expired: the tool is not called, the node fails as
    `APPROVAL_REJECTED` outside its retry policy, and the run records that
    error code;
  - approved: the call runs, as before.
- **Two decisions on one request could both be taken.** `POST
  /api/v1/observe/approvals/{id}/resolve` decided without a lock. The request
  is now locked while it is decided: exactly one decision is taken, the same
  decision again returns the request unchanged, and a different decision on
  a closed request answers `409`.
- **Canceled requests and ended runs left work waiting.** Canceling a
  request now sends `approval.canceled`, which releases a waiting task as a
  rejection does. An approval sweeper closes pending requests whose run has
  ended as `canceled`, against `system`.

Agent runs and direct tool calls already acted only on an approved decision
and are unchanged.

## Database Compatibility

- Fresh installations migrate from `base` to `20261002120000`.
- This release adds no migrations: a v1.6.0 database needs none.
- The supported N-1 upgrade range stays `20260927160000..20261002120000`.

## Upgrading

1. Nothing to migrate. Restart the API and workers on the new images.
2. Enable the approval sweeper on the API service if you do not use the
   shipped compose files: `APPROVAL_SWEEPER_ENABLED=true` (and optionally
   `APPROVAL_SWEEPER_INTERVAL`, 30 seconds by default). Its first sweep
   closes the pending requests of runs that already ended.
3. Behaviour changes to review:
   - A client that resumed workflow runs without a decision now gets `409`
     until the request is approved, rejected or canceled.
   - A different decision on a closed request is `409` (it was `400`); the
     same decision again is `200` with the request unchanged (it was `400`,
     or `500` when sent at the same moment).
   - A task released by a canceled request fails with `approval_canceled`.
4. Look for tool calls that ran without an approval. On PostgreSQL:

   ```sql
   SELECT a.run_id, a.id AS approval_id, a.status AS approval_status, t.tool_ref
   FROM approval_requests a
   JOIN run_step_tool_calls t
     ON t.run_id = a.run_id
    AND t.tool_call_id = a.details_json ->> 'tool_call_id'
   WHERE a.status <> 'approved'
     AND t.status = 'succeeded';
   ```

   Each row is a call that succeeded although its request was not approved.

## Known Limitations

- Approval requests have no assignee or deadline yet: any workspace member
  with write access decides any request.
- A workflow approval decision does not resume the run on its own; resume it
  through the API or the console.
- The known limitations of v1.6.0 still apply.
